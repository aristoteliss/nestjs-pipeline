A job runs after the request that enqueued it is gone. With
[`@nestjs-pipeline/job-context`](/nestjs-pipeline/packages/nestjs-pipeline/job-context/), the
job carries the request's tenant, correlation id and principal, and restores them before it
runs, so a pipeline it dispatches makes the decisions the request would have made. This
recipe follows the welcome email of [A command through every
layer](/nestjs-pipeline/recipes/command-pipeline/).

## 1. Register the module

`AppModule` registers it once, with the application's principal port, the tenants a job may
run in, and the stores the tenant and correlation id are read from:

```ts
JobContextModule.forRoot({
  principal: SessionJobPrincipal,
  tenants: () => persistenceConfig().tenants,
  sources: contextSources,
  imports: [AuthsModule],
}),
```

`tenants` is a function, read when the application starts, so the list comes from the same
configuration as the database.

A payload is data: anyone who can write to the queue can write it. So it carries an identity

now. `SessionJobPrincipal` reloads the session, so a revoked session or a deleted user
