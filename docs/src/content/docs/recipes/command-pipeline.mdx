This recipe follows `POST /users` of users-api, the repository's example application. Every
file below is the application's real code, shown as it is built and tested.

## 3. The handler declares its pipeline

`@UsePipeline` stacks the behaviors this command needs. They run after the global `before`
behaviors and in the order listed (see [Pipeline execution
model](/nestjs-pipeline/concepts/execution-model/)):

| Behavior | What it does here | Package |
| --- | --- | --- |
| `logging` | Logs the command; a duplicate email (`UniqueEmailException`) logs as a warning, not an error | [core](/nestjs-pipeline/packages/nestjs-pipeline/core/) |
| `requires` | The type-level check: the caller may `create` a `User` at all | [casl](/nestjs-pipeline/packages/nestjs-pipeline/casl/) |
| `featureFlag` | Refuses the command while the `user-registration` flag is off | [feature-flags](/nestjs-pipeline/packages/nestjs-pipeline/feature-flags/) |
| `rateLimit` | Spends `RATE_LIMIT_COST.createUser` points from the caller's bucket | [rate-limit](/nestjs-pipeline/packages/nestjs-pipeline/rate-limit/) |
| `idempotent` | Replays the result of a retried operation with the same `Idempotency-Key`, for the same caller and permissions | [idempotency](/nestjs-pipeline/packages/nestjs-pipeline/idempotency/) |
| `audit` | Records who created which user, and the outcome | [audit](/nestjs-pipeline/packages/nestjs-pipeline/audit/) |

Inside `handle`, `CaslAuthorizer.authorize` checks the new entity and the fields being
written. That entity-level check belongs in the handler, after the aggregate exists; the
type-level `requires` above cannot see the entity. `CommandBaseHandler` then publishes the
aggregate's buffered events once `handle` returns:
